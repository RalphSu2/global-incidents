# Anthropic (Claude) — platform.claude.com 用量数据加载报错

> **分级：B 级** · 仅厂商状态页事故记录，**厂商未发布技术复盘**
> 原始报告归档：[`raw/official-report.html`](raw/official-report.html)

## 一句话结论

Claude Console（platform.claude.com）的 **Usage 页、Rate limits 页和 Admin API 用量报表**无法正常加载；厂商明确 **API 请求与核心功能不受影响**，因此这是一次**纯观测面故障** —— 不影响业务，但影响客户对账。

## 技术要点

> 解读：以下是基于状态页文本的分析，**属于我的判断，非厂商陈述**。

**1. 故障域被清晰地限定在"用量聚合链路"**

受影响面精确落在三个**读取用量数据**的位置：
- `platform.claude.com` → Usage 页
- `platform.claude.com` → Rate limits 页
- Admin API → usage report

而**API 请求本身明确不受影响**。这是一条典型的"控制面/观测面故障、数据面正常"的分界。

**2. 用量数据有固有的延迟窗口（约 30 分钟）**

> 原文：*"the most recent ~30 minutes of usage may take longer to appear"*

厂商自己承认 30 分钟的数据延迟属于正常范畴。这暗示用量数据是**异步聚合**的（批处理/流式汇总），而非实时查询 —— 一旦聚合管道出问题，前端展示就会同时空白。

**3. 报表恢复先于页面恢复**

Admin API 报表先恢复，platform.claude.com 的 Usage / Rate limits 页后恢复。这说明两者走**不同的读取路径**：API 直连聚合结果，页面还要经过额外的服务层。所以"底层好了"不等于"页面好了"。

**4. Rate limits 页与 Usage 页同源**

Rate limits 页也一起挂了，说明限流额度的展示依赖**同一份用量聚合数据**。这是一个值得注意的设计耦合：观测组件与被观测的计费/限流数据共用同一条管道。

## 与我们相关的启示

> 解读：以下是我的分析，非厂商原文。

**① 观测面故障不会中断业务，但会烧掉信任**

API 请求全程正常，业务零中断。但对客户来说，"我看不到用量和账单"和"服务挂了"在心理上是接近的 —— 尤其对按量计费的客户。**观测面的可用性目标应该单独定义，不能和业务面混为一谈。**

**② 用量/账单展示要有"降级态"而不是"空白态"**

既然聚合管道必然有延迟和故障窗口，前端就应该设计成：显示"数据延迟至 HH:MM"或"最近一次成功聚合时间"，而不是直接报错或显示空白。**能展示数据陈旧度，比展示一个错误页好得多。**

**③ 别让限流展示依赖计费聚合管道**

Rate limits 页和 Usage 页同源挂掉，说明限流视图被绑在用量聚合上。限流状态的读取路径**应当独立于计费聚合**，否则观测链路的抖动会同时打掉两个不同用途的面板。

**④ 状态页时长不可用于 SLO 统计**

这条事件把"状态页跨度 6 天、实际影响可能不到 1 天"的偏差暴露得很清楚。任何基于状态页历史做可用性计算的方案，都必须先区分**事件实体**与**状态页条目开闭时间**。
