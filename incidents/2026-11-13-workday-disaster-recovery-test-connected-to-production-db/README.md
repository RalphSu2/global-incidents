# Workday — 灾备演练把 DR 环境连到了生产数据库

> **分级：C 级** · **厂商未发布技术报告**，仅在客户状态页给了一段根因说明。

## 一句话结论

**为了验证"扛得住故障"而做的灾备演练，本身制造了一次故障。** 在验证每周维护窗口时，DR 站点内的租户服务意外连上了生产数据库，导致数据进入不一致状态，客户约 18 小时无法打卡、查工资、请假。

---

## 时间线（UTC，2026-11-13/14）

| UTC | 事件 |
|---|---|
| 11-13 **20:24** | 故障开始（客户开始报告打卡、薪酬、请假功能异常） |
| — | 厂商将**全部 WD1 生产租户**置入 maintenance，做 reindex + tenant release |
| 11-14 **~16:00** | 大部分客户恢复（累计约 1056 分钟） |

> ⚠️ 结束时间是"大部分客户恢复"的约数，长尾客户恢复显著更晚。

## 根因（官方口径）

客户状态页原文（这是厂商给出的**唯一**技术说明）：

> *"While validating the weekly Maintenance Window for **Disaster Recovery tenants**, we have identified that **tenanted services within the DR Site unexpectedly connected to Production databases**. As a result, this has left data in an **inconsistent state** that can cause errors accessing tenants or jobs/integrations/tasks to fail with missing transaction error messages."*

**处置**：把全部 WD1 生产租户置入 maintenance 状态，执行 reindex 与 tenant release。

## 技术要点

> 解读：以下为我的分析，非厂商原文。

**1. DR 环境与生产环境之间的隔离失效了**
灾备站点的设计前提是"与生产完全隔离"。一旦 DR 的租户服务连上生产库，就会以生产库的身份写入/读取，破坏事务一致性。

**2. 数据不一致比服务中断更难处理**
服务挂了可以重启；数据进入不一致状态后，必须做 reindex 才能恢复，而且**客户无法自证数据是否完整**。这是企业 HR/财务系统的关键风险面。

**3. 维护窗口验证 = 在生产邻近环境做写操作**
"验证维护窗口"听起来只是检查流程，实际会触发连接建立与读写。**这类验证本身就是变更**，风险等级应等同于生产变更。

**4. 影响面是"全部 WD1 生产租户"**
不是个别客户，是全量。这解释了为什么持续时间这么长 —— 要做全量 reindex。

## 与我们相关的启示

> 解读：以下为我的分析。

**① 灾备演练必须在网络层强制隔离** —— 不要靠配置保证 DR 连不到生产，要靠网络策略/SG 硬隔离。

**② 演练的风险等级要等同生产变更** —— 尤其是会建立数据库连接的"验证"动作。

**③ 数据一致性故障需要有对外自证手段** —— 客户会问"我的数据对不对"，厂商要有可核查的报告。

**④ 记录这个反模式** —— 弹性机制变成故障源，这类案例值得单独归类。
